# log.mdとgit logの分工

「git管理下のwikiではcommit messageで操作履歴を賄えるのでlog.mdは不要では？」という論点を、subagent相談2往復で検証した記録。結論: **部分的正しく、全体としては誤り**。ただし機械的部分（日付+操作種別）はgit logと重複するため、肥大化対策として軽量化すべき。

## 論点

ある研究者の主張:
- git管理していないwikiならlog.mdは有用
- しかしgit管理下では、commit messageにlog.mdと同等の情報を含めれば操作履歴の役割を果たす → log.md不要
- log.md肥大化問題（grasp 334KB/2,018行）も発生しない
- git commitは時刻情報が正確なので、時系列情報もgit logのほうが正確

## 検証結果

### 1. gitは「コミット時刻」を測る。「操作時刻」ではない

log.mdが記録したいのは**操作というイベントの時刻**だが、git logが記録するのは**コミットというイベントの時刻**。測っているものが違う。

- 人間が操作後にまとめてcommitする運用（推奨される運用）では、操作時刻とコミット時刻は数日〜1週間ずれる
- log.mdの日付はLLMが操作時点で書くので、操作の時系列として測っている対象が近い
- 逆の弱点: log.mdの日付はLLM作文ゆえ±1日の誤記余地があるが、「流れの把握」用途では実害なし
- gitの「正確さ」は、実害のない方向（コミット時点）にだけ正確

### 2. gitの時系列は書き換わり得る。log.mdは構造的に不変

- squash/amendはcommitter dateをnowに書き換え、rebase・cherry-pick・force-pushは履歴ごと消える
- log.mdは追記専用規約なので、過去エントリは構造的に不変（履歴書き換えはワーキングツリーに触れない）
- 「書き換えられる正確さ」より「書き換えられない曖昧さ」のほうが実用上堅い

### 3. 用途の混同: 監査の精度要求を流れ把握に持ち込む

「正確な時刻」を要求する用途（rollback・blame・監査）に必要なのは時刻ではなく**コミットの同一性（hash）と差分**であり、それはgitの本来用途。log.mdの用途は「最近の操作の流れの把握」＝順序＋意味で、日粒度で十分。

補足: 操作順序ですらgitは厳密には保証しない（同日コミットの順序、タイムゾーン、`--date`表示問題）。

### 4. log.mdにしか書けない情報（git diffから復元できないもの）

1. 操作の動機・きっかけ（「きっかけ: 〜という気づき」）
2. 未解決の疑問・open question・保留された仮説（コミットは解決済みしか含まない）
3. 人間との対話の要約（subagent相談、却下された代替案、人間の判断）
4. 破棄された選択肢とその理由（gitは現れたものしか見せない）
5. 操作単位のページ間関連（1操作=10〜15ファイルのまとまり。gitはファイル単位）
6. ステータス遷移の履歴（hypothesis → tentatively-adopted 等の経緯）
7. 次へのアクション提案（「次は〜」の手渡し）

### 5. 「commit messageで賄う運用」の失敗シナリオ

| シナリオ | 結果 |
|---|---|
| 人間のまとめコミット（推奨運用と直結） | 操作時系列はコミット時刻の1点に潰れる。「先週何をした？」に答えられない |
| 1操作15ページ | commit messageに全ページを書くのは非現実的（「ingest X」で済まされる） |
| 混在repo（wiki+コード） | commit message検索がコード操作のノイズに埋もれる |
| Obsidian衝突 | 人間はgit logを視点として見られない。Karpathy型のObsidian IDE運用ではlog.mdはそのまま読める |
| コミット対象にならない情報 | 検討中・破棄した案・未解決事項はdiffに現れない |
| message品質の劣化 | 操作時刻とコミット時刻の乖離が大きいほどmessageは薄まる（記憶減衰・「update」コミット） |

### 6. 永続性: log.mdはrepo属性ではなくwiki成果物

| 状況 | git log | log.md |
|---|---|---|
| squash / rebase -i / amend / cherry-pick / force-push | 書き換わる・消える | **生き残る**（ワーキングツリー無傷） |
| shallow clone | 過去が消える | **生き残る** |
| 株分け・コピー・テンプレート配布・別サーバ移転 | 付いて行かない | **付いて行く** |
| repo破棄・ディスク喪失 | 消える | 消える（引き分け） |

株分けは有利な非対称を生む: **子wikiは親の操作史を持てる**（出自の証跡・プロベナンス）。「log.mdをそのままコピーして派生エントリを冒頭に足す」が可能で、git historyではこの選択肢自体が存在しない。

### 7. 粒度のトリレンマ

(a) 1操作1コミット → git logは綺麗だがページ単位の履歴が不正確
(b) ページ単位コミット → 1操作が10〜15コミットになり操作のまとまりが消滅
(c) バッチコミット → 日次の操作記録が失われる

log.mdは「操作のまとまり」を1エントリで表せる唯一の媒体。

## 既存議論の調査

「log.md廃止・git log完全代替」を明確に主張する既存論は、英語・日本語とも見つからず。見つかったのは以下の系統:

1. **Diors.tech「Git 工作流」**（https://diors.tech/blog/092-llm-wiki-git-workflow/）: 「Git + log.md の分工」節で本論点を直接扱う。結論: 両方必要（Git=ファイル履歴/diff/ロールバック、log.md=知識操作タイムライン・人間可読文脈）。ただし理由付けが「人間可読」に限定されており、第一読者がLLMであること（ツール非依存・未コミット情報・操作単位のまとまり）を見落としている
2. **CHANGELOG vs git logの古典論争**（最良の先行議論）:
   - Keep a Changelog: git logは本質的にノイズ。commitは進化の一原子ステップ、changelogは状態間の注目すべき差異
   - agateau.com "Your git log is not a changelog": commit messageは「なぜこのコミットは存在するか」、changelogは「利用者が何を気にするか」
   - 反対派（HN kazinator）: ChangeLogはcommit messageと冗長 — ただしこれはGNU ChangeLog（機械的記録）への反論であり、NEWS（人間向け要約）は別物として残された。この区分はlog.mdに適用できる: **機械的部分（日付+操作種別）はgit logと重複（不要論の言い分が正しい）だが、意味論的部分（why・未解決・次）はNEWS相当で重複しない**
3. **graspの進化**（[[リポジトリ分析 grasp]]）: log.md 334KB →「git logでもなくlog.mdでもない第三の層」（SQLite events table）へ進化。log.mdは置換でなく**第三の層として追加**。操作履歴は「ファイルの変更」でも「コミット」でもなく、それ自体が一級の知識資産という実証

## 実証データ

- パイロット5件すべてがgit運用下でもlog.mdを維持している（[[パイロット分析 横断所見]]）
- 当wikiはgit管理下で運用中だが、log.mdは2週間で肥大していない。2026-08-14にエントリ形式を「見出し = `## [DATE] action | 短い題名` + 詳細は本文」に変更（rendering時の見づらさ解消。既存エントリは情報保持のまま再整形）
- graspの爆発はエントリ本文に長文を書いたことが直接原因。自動化（ship loop）が増幅

## テンプレートへの示唆

- log.mdはテンプレートに含める（デフォルトあり、オプショナル削除可）。「git管理なら不要」オプションは提供しない
- 軽量化をデフォルト規約に:
  - 見出し1行規約（`## [DATE] action | 短い題名`）+ 詳細は本文。見出しに長文を入れない（rendering可読性のため。当wikiで実証済み）
  - 500エントリ or 100KBでローテーション（`log.archive-YYYYMM.md` へ退避。git管理下なので歴史は残る）
  - lint項目に「log.mdサイズ」を追加
  - 「log.mdに書かないもの」をAGENTS.mdで定義（日常のマイナー編集・機械的フォーマット修正はlog不要）
- AGENTS.mdのlog.md記述の推奨形: 目的を「機械的な操作履歴」ではなく「LLMと人間のための、最近の状況把握と未解決事項の手渡し」と明記

### 推奨AGENTS.md文案（テンプレート用・薄く）

```markdown
## log.md（追記専用の操作記録）

- wiki/への全操作（ingest / query / file-back / refactor / lint / adopt / split 等）を
  1エントリで時系列に記録する。見出し: `## [YYYY-MM-DD] action | 短い題名`、詳細は本文（body）。
- 役割は「操作の流れと背後にある事情」（なぜ・未解決事項・次への手渡し・人間との対話の要約）。
  ページの内容や変更の詳細は書かない（diffで見られる）。git logの代替ではなく補完:
  - git log = ファイル履歴（ページ単位の差分・blame・rollback。コミット日時であり操作日時ではない）
  - log.md = 操作記録（操作のまとまり・事情。追記専用で履歴書き換えに耐える）
- コミットされない情報（検討中・破棄した案・未解決事項）こそここに残す。
- 過去エントリは編集・削除しない。間違いは新しいエントリで訂正する。
  （例外: 形式変更は情報を保持したままの再整形に限り、2026-08-14に実施実績あり）
- 肥大化対策: lintでサイズ上限チェック（例: 500エントリ / 100KB）。
  超過時は古い分を log.archive-YYYYMM.md へ切り出してローテーションする。
```
