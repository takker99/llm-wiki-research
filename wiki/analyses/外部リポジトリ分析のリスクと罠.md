# 外部リポジトリ分析のリスクと罠

[[GitHubリポジトリ分析の方法論]]から分離。
実際のLLM Wikiリポジトリを収集・分析する際に陥りうる罠と、その対策・認識すべき限界をまとめる。

---

## 1. ライセンス・法的・倫理

### 派生物問題

`wiki/` に生成される分析ページ（concepts/, analyses/）は、分析対象repoのAGENTS.mdやwikiページの
「派生物（derivative work）」に該当する可能性がある。
引用の範囲を超えて他者のAGENTS.mdの構造・ルールを再現すると、ライセンス違反になりうる。
研究目的の引用（Fair use / 引用権）と、テンプレートという成果物への転用は法的に別物。

### ライセンス不在

LICENSEファイルがないrepoはAll Rights Reservedがデフォルト。
AGENTS.mdやwikiページの分析・引用には著作者の明示的許諾が必要になる可能性がある。
分析前に対象repoのライセンス確認を必須ステップにする。

### 同意の不在

公開リポジトリだからといって「研究対象にされることへの同意」があるわけではない。
作者が自分のLLM Wikiがケーススタディとして解剖されることを予期していない可能性が高い。
特に個人系Wiki（家計LLM-wiki、猫LLM Wikiなど）は作者にとって私的な実験であり、
運用パターンを公的な研究成果として抽出されることは想定外かもしれない。

### 学習データ転送の二次リスク

この研究Wiki自体が公開されると、他者のAGENTS.mdから抽出されたパターンが
将来のLLM訓練データに混入し、原作者の想定を超えた流通が起きる。

### 対策

- 分析対象repoのライセンス確認をingest前ステップに組み込む
- manifest.mdにライセンスフィールドを追加
- 個人系Wikiは特に慎重に扱い、可能なら作者に一声通知（インタビュー機会にもなる）
- 許諾的ライセンスがないrepoの扱い基準を事前に決める

## 2. 分析の質の罠（6類型）

### 2.1 文書化バイアス（Documentation Bias）

AGENTS.mdは「こう運用すべき」という**規範**であり、wiki/は**実際の結果**。両者は乖離しうる。
例えば「ファイル名は自然言語」とAGENTS.mdに書いてあっても、実際のページがkebab-caseばかりというケース。

- **検出方法**: 各repo分析時に AGENTS.mdの規範 vs wiki/の実態 の乖離チェックをlint項目に追加
- **なぜ重要か**: 規範だけ見て「このパターンが良い」と判断すると、実態とかけ離れたテンプレートになる

### 2.2 観測不能問題

git historyからは「その編集をしたのが人間かLLMか」が判別できない。
LLM Wikiの核心である「LLMが自律的にwikiを保守する」度合いを、
公開repoの静的なスナップショットからは測定できない。
コミットメッセージが `docs(wiki): ...` でも、プロンプトを書いたのは人間かもしれない。

- **部分的手がかり**: コミットauthor情報（noreply@github.com のbotアカウントか等）で推定は可能。限界は認識
- **なぜ重要か**: 「LLMが自律運用する度合い」はテンプレート設計の核心的関心事だが、直接観測できない

### 2.3 初期条件バイアス

最初の3〜5 repoがnishio系だと、それ以降のrepoを「nishio系からの差分」として評価してしまう。
Pythonの設計判断を「C言語からの差分」で評価するような歪みが入る。

- **対策**: 独立系repoの意識的探索。設計空間マップで複数の見方を用意
- **現在の状況**: 公開されているLLM Wikiの大半がnishio系。このバイアスを回避するのは構造的に困難

### 2.4 再帰問題（Recursive Lens Distortion）

自分のwikiの4分類（concepts/entities/sources/analyses）というレンズを通して他repoを見ると、
この4分類を投影してしまい、それ以外の構造パターンを見逃す。
現在のwikiの分類体系は仮説（[[テンプレート草案ver.1]] claim#2）であり、分析対象に対して中立ではない。

- **例**: concepts/entitiesの区別がないwiki、categories/ではなくtags/で整理するwiki 等のパターンを見落とす
- **対策**: 設計空間マップで複数の分類軸を用意。自分のwikiの分類を当然視しない

### 2.5 氷山問題（Iceberg Problem）

公開repoはLLM Wiki全体の可視部分に過ぎない。
プライベートrepoのLLM Wiki、ローカルのみのWiki、破棄された実験は観測できない。
nishioのデータが示すように、最も成功している個人系Wikiは公開されていない可能性が高い。

- **含意**: 公開repoの傾向が「LLM Wiki一般」の傾向とは限らない
- **対策**: 発見の限界を明示する。統計的一般化を避け、パターンの多様性カタログ化に留める

### 2.6 原因と結果の混同

成功しているWikiに共通する特徴（例: index.mdがある、概念ページ数が多い）を「best practice」とみなすと、
それらが単にテンプレートのデフォルトだったり、LLMが自律的に生成した副産物に過ぎない可能性を見逃す。

- **テンプレートの自己実現的予言**: このwikiで良いと判断したパターンをテンプレートに入れる → そのテンプレートを使った人がそのパターンを踏襲する → 「やはりこのパターンが良いという証拠が増えた」となる循環
- **対策**: テンプレート由来か独自進化かの区別を常に意識する

### 2.7 生存者バイアスとその深化

- **生存者バイアス**: 公開され更新が続いているrepoだけが分析対象になる。放棄されたWikiは公開されないか削除される
- **初期採用者バイアスの深化**: 現在の公開LLM Wikiはほぼnishioの知的系譜（Cosense→Scrapbox文化、KJ法的思考、日本語コミュニティ）に染まっている。英語圏の独立した実践者がいれば全く異なるパターンを示す可能性

## 3. プロジェクト管理リスク

### スコープクリープ

集めるべきリポジトリの数が際限なく増える。
「何repo集めたら十分か」の基準がない。サチュレーション（新パターンが出現しなくなる）を基準にできるが、
その判断には全repoの分析が先に必要という循環がある。

- **対策**: パイロット3 → 拡大10 → 飽和チェック の段階的進行。各段階でGo/No-Go判断

### 比較分析の指数的複雑性

「Repo AのAGENTS.mdはX、Repo BはXの変種Y」という比較がリポジトリ数nに対して O(n²) で増大する。
ingestの「1ソースが10-15ページに触れる」が、比較分析では「Nリポジトリ間の差分マトリクス」に拡大する。

### 再分析コスト（Technical Debt）

分析フレームワークを途中で変更すると、それまでの全ページ（sources/, concepts/, analyses/）が
technical debt化する。最初の分析が浅いと判断して再分析するときの修正コストが高い。

- **対策**: 小規模（3 repo）のうちに枠組みを安定させる。再分析用の修正プロトコルを事前定義

### 「LLM Wiki」の操作的定義の循環

どのrepoを収集対象とするかという判断自体が研究のアウトプットに依存する。
「LLM Wikiとは何か」の定義は研究が進まないと固まらないが、定義なしには収集対象を決められない。

- **現在の運用定義**: AGENTS.md に ingest/query/lint ルールがあるrepo
- **リスク**: この定義自体がテンプレート草案の鏡像になっており、テンプレート非依存のパターンを発見できない

### 発見層の管理負荷

`raw/` 外にcloneしたrepo群（発見層）が増えると、
どのrepoのどのバージョンを分析したかの追跡が複雑化する。

## 4. 情報の劣化リスク

### スナップショットの陳腐化

分析後に元repoが更新された場合、分析結果が古くなる。定期的な再チェックが必要だが、
そのコストはrepo数に比例する。

### git履歴の喪失

`git clone` でHEADだけを取ると、AGENTS.mdやwiki構造の**進化の軌跡**が失われる。
初期のAGENTS.mdと現在のAGENTS.mdの差分こそが「何がうまくいき何が捨てられたか」の重要なデータ。

- **対策**: 特に興味深いrepoのみ、後で `--mirror` 等で全履歴を取得して深掘り

### メタデータの欠落

repoのissue、PR、discussionには「なぜその設計判断をしたか」の議論が残っている可能性がある。
cloneだけではこれらの運用文脈が欠落する。GitHub APIでissue/PRも収集対象に含めるか、事前に判断が必要。

### 削除・非公開化

分析後にrepoが削除された場合、公開研究成果として引用しているURLがデッドリンクになる。
`manifest.md` にcommit hashを残すだけでは不十分で、Web Archive等の永続的参照の仕組みが必要。

## 5. 見落としパターンのリスク

### AGENTS.md非依存パターン

現在の枠組みは「AGENTS.md = 運用ルール」が前提だが、
実際には `.claude/`, `.opencode/` のスキルファイル群、`CLAUDE.md`、Cursor Rulesなど、
機能は同じでファイル名・形式が異なる設定が使われている可能性がある。
tsurubeeの例（[[テンプレート草案ver.1]] evidence）では `CLAUDE.md + 4スキル + vault/` という構成が確認されている。
AGENTS.mdを前提とした収集ではこれらの亜種を取りこぼす。

### マルチエージェント構成

単一のAGENTS.mdではなく、複数のエージェント設定ファイルを持つrepoが存在する可能性。
subagentごとに異なる運用指示がある場合、単一の「運用ルール」としての分析では不十分。

### CI/CD統合型Wiki

GitHub Actions等でingestやlintを自動化しているrepo。
これらの自動化パターンはAGENTS.mdにもwiki/にも現れず、`.github/workflows/` や scripts/ にしかない。

### ハイブリッド運用

「LLMが管理する」という前提自体が成り立っていないが、表面的にはAGENTS.mdとwiki/を持つrepoが存在しうる。
人間が主導しLLMが補助するパターンと、LLMが主導するパターンは根本的に異なるが、静的分析では区別できない。

## リスクマトリクス（深刻度×検出難易度）

| リスク | 深刻度 | 検出難易度 | 現時点の対策 |
|---|---|---|---|
| ライセンス・派生物問題 | 高 | 低（ライセンス確認で検出可） | 事前ライセンス確認を必須化 |
| 文書化バイアス | 高 | 中（比較分析が必要） | lint項目に追加 |
| 初期条件バイアス | 高 | 高（自分では気づきにくい） | 独立系repoの意識的探索 |
| 再帰問題 | 中 | 高（無自覚になりやすい） | 設計空間マップで複数の見方 |
| 氷山問題 | 中 | 不可（観測不能） | 限界を明示 |
| 観測不能問題 | 中 | 不可（git logからは判別不可） | コミットauthor情報で推定 |
| 原因と結果の混同 | 中 | 中（注意深い分析が必要） | テンプレート由来か否かの区別 |
| Technical debt（再分析） | 中 | 低（変更時に顕在化） | 小規模段階で枠組み安定化 |
| スコープクリープ | 低 | 低（進行中に気づく） | 段階的進行＋Go/No-Go判断 |
