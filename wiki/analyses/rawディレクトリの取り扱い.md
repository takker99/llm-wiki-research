# rawディレクトリの取り扱い

`raw/*` はgitignoreされており、`raw/` はgitの管理外にある（karpathyのgistすらuntracked）。
この状態は意図的なものだが、トレードオフを整理し、テンプレートのデフォルトをどうするかを検討する。
一部は[[Cosenseソースのingest方式]]（2026-08-11）で仮採用済み（manifest.md・発見層の分離・lint対応）。

## gitignoreの動機（ユーザーによる意図、2026-08-11）

- **graspのrepoが同様の運用**をしていた: `raw/`=外部ソース（設計対話ログ・Codex作業ログ等）、不変・gitignored（grasp commit a7ff7d3 で確認）
- **privateな情報**を入れたとき、git logにデータを残すのはまずい
- **論文PDFをそのまま入れると転載**になる（著作権）
- **repoをsourceとしたとき、その全部をraw/に入れるのか？** という疑問
- private repoでやるぶんには全く問題ない

注: 「発見層とrawの区別」はgraspの設計ではなく、[[Cosenseソースのingest方式]]側のフレーム。
graspで発見を担うのはSQLite store + CLI（`~/.grasp`、これもgitignored）で、raw/はあくまで外部ソース置き場。

### grasp・nishio系wikiでの検証（2026-08-11）

grasp本体の全履歴（commit e3c9625〜a7ff7d3）を調査した結果:

- `raw/` のgitignoreは**初期scaffold（create_wiki.py）に最初から含まれており**、以降変更なし。**判断プロセスの記録はgrasp内に存在しない**（テンプレートのデフォルトとして継承されたと推定）
- 理由が明文化されているのはnishioの派生wiki `llm-wiki-about-nishio`:
  - .gitignoreコメント: 「Large source corpus (**regeneratable** via `git clone ...` raw/external_brain_in_markdown)」— **再生成可能だからignore**
  - AGENTS.md: 「本Wiki repo は public なので、raw/ には公開Cosense由来のbundleのみを置く。**private project / 非公開ソースは絶対に混入させない**」
- **実運用前例**: `llm-wiki-about-nishio` は raw/ にgit cloneを丸ごと配置（`raw/external_brain_in_markdown`、gitignored、`git pull`で更新可）。URLは.gitignoreコメントとAGENTS.mdに記録。→ 今回の「repoをraw/にclone」議論の先行実装であり、「clone丸ごと+gitignored+再生成可能」という選択肢の実証

→ この発見は下記「テンプレート設計への含意」の「gitignoreのデフォルト」「manifest.md」にインプットする。

## gitignoreの二面性

| 面 | 内容 |
|---|---|
| 負 | バックアップ・履歴なし。**2026-08-11の6ファイル誤削除の直接原因**（[[Cosenseソースのingest方式]] line 24） |
| 正 | private情報のgit log残留防止、著作権のある資料の転載防止。**プライバシー・著作権の防御として機能** |

[[Cosenseソースのingest方式]] は負の面だけを記録していたため、正の面（防御としての機能）をここで補足する。

## 既存提案との接続: 発見層とrawの分離

[[Cosenseソースのingest方式]] の「発見層 → 生読み → 引用時アーカイブ」パイプラインは、
raw/全体の取り扱いに一般化できる仮説:

1. **発見層**: 大きなソース集合体（Cosense DB / 分析対象repoのclone）は `raw/` 外に置く
2. **生読み**: 探索・分析は発見層に対して行う
3. **引用時アーカイブ**: 実際に参照・引用したファイルだけを `raw/` にコピー
4. **manifest.md**: URL・commit hash・取得日・ハッシュを記録し、**コミット対象にする**（`raw/*` はignoreされたままなので、manifest.md はネガティブパターンでコミット対象に復帰させる）

## repoをsourceとした場合の適用（2026-08-11の議論）

「llm wiki実践例repoの運用分析」のケース:

- cloneは `raw/` 外（`~/git/` や `/tmp`）に置く = 発見層
- 分析で実際に引用したファイル（AGENTS.md、index.md、ディレクトリツリー等）だけを `raw/<repo>/` へ
- manifest.md にURL・commit hash・取得日・対象ファイル一覧
- これで「repo丸ごとをraw/に」の否定と「無管理の引用」の両方を避ける

lint上の注意（2026-08-11解決）: 参照チェックは `raw/` 直下の `.md` しか見なかった（正規表現がスラッシュを含むパス・空白入りパスに非対応）が、[[Cosenseソースのingest方式]]8に従いlint.shを修正済み。

## テンプレート設計への含意（草案ver.2のclaims候補）

- **gitignoreのデフォルトはどちらか**: 公開repoなら「commitして配布」が自然だが、private情報・著作権の観点ではignoreにも理がある。公開/非公開で挙動を変えるかも論点
- **manifest.mdのコミット対象化**は損失防止の防衛線として有力（gitignoreと両立可能）
- 発見層とrawの区別はデフォルトのAGENTS.mdに書くか、応用編に置くか（薄さの維持との兼ね合い）
- gitignoreのままなら**バックアップの代替手段**（別途の定期バックアップ等）をどうするか

## 不変性の設計思想の整理（2026-08-14、subagent相談2往復）

「raw/は実態として『不変のアーカイブ』ではなく『単なる情報源の置き場』では？」という問い（Karpathyの不変 vs nishioの実運用は不変でない vs このrepoのgitignore）から、不変性の設計思想を整理した。

### 2類型の混在（観察の修正）

「単なる置き場」という一般化は部分正しい。raw/には2種類のものが混在している:

| 型 | 例 | 不変性の状態 |
|---|---|---|
| スナップショット型 | `raw/cosense/` 配下の日付付きアーカイブ（追記のみ） | 規則として実装 |
| ライブ型 | nishioの `external_brain_in_markdown`（gitignored + `git pull`更新） | 実際は「単なる置き場」 |

ライブ型の解決（発見層分離+引用時アーカイブ）は既に仮採用済み。正しい読みは「raw/は2種類の混在場所であり、**不変性を定義に使うとライブ型を説明できない**」。

### 入場時の誓約（admission-time commitment）

不変性を「ソースの性質」から「**アーカイブ時点以降の誓約**」に移す: raw/に書き込んだ時点の内容で凍結される。ソース自身が静的である必要はない（ライブソースのスナップショットも矛盾なく説明できる）。

実務上の価値:
- **性質文→時間規則への書き換え**: 「raw/は不変・絶対に変更しない」はLLMが執行しにくい性質文で、例外条項（`唯一の例外:`）が必要になる。時間化（「書き込んだ時点で凍結」）すればアーカイブ追記は例外ではなく**規則の定義そのもの**になり、例外条項が消える
- **命名・ハッシュの意味論**: `<title>-<YYYY-MM-DD>.md` の日付とmanifestのsha256は「いつ凍結したか」「凍結時点の指紋」の帰結であり、「同一内容の再取得はハッシュ照合で省略可」を成立させる
- **入場テスト**: 「この時点の内容を凍結できるか？」→ 追従したいソース（clone等）は自動的にraw/の外（発見層）へ
- **規則の統合**: 引用時アーカイブとappend-onlyは同一コミットメントの表裏で、2規則が1規則に（AGENTS.mdの薄さに貢献）

注意: これは経験的発見ではなく説明概念。単独では反証不可能で、価値は導出される設計claims（文言変更・入場テスト）の検証可能性にある。

### 不変性の3機能

| 機能 | 内容 | 誰への効果 |
|---|---|---|
| 検証可能性 | 争われたら同じ内容に遡れる（Karpathyの原理） | 認識的 |
| 書き換え自由の担保 | source of truthをraw/に固定することでwiki/の自由な更新・削除が可能になる（nishio: 「追記追記になってしまう」問題の回避） | 行動的（wiki側） |
| LLMの範囲境界 | wikiが汚れてもlint可能だが、ソースが汚れると検証基準そのものが腐る。LLMがソースを「改善」したくなる誘因へのカテゴリ境界 | 行動的（ソース側） |

第三機能の派生規則: **変換・整形は入場時のみ許可**（Cosense記法→Markdown変換は入場時に実施。入場後の「整形」が腐敗事例）。3層は「LLM書込権なし/書込権あり/共進化」という権限マップとして読める。

### 安定性の3要素と非対称な二段構え

証拠は「**内容+時点+同一性**（URL/タイトル）」の3要素。二段構えは対等な複製ではなく非対称な役割分担:

- スナップショット = 引用の対象（wikiの主張の検証先は常にこれ）
- ライブURL = 再検証・発見のプローブ
- ハッシュ = 差分検出の橋（ライブが変化して主張が争われたら、再取得→ハッシュ照合で機械判定）

「ソース・オブ・トゥルース」の二義性も解消される: ライブソースは「外部世界の真実」、raw/は「wikiの真実」。wikiの主張の検証先は常に後者。

### gitignore論争の新軸

- 「**git=無償の不変性担保**」は撤回。正しくは**可監査性・復旧性**（diff/revert）。不変性は社会的コミットメントであり、gitは執行メカニズム。ただしパターンの脅威モデル（LLMの事故的改変・人間の誤操作）には実効十分
- **public/privateの二分は不適切な軸**。正しい軸は「**repo可視性 × ソースの転載可能性**」: 転載可能なソース（gist・公開Cosense）なら追跡可、転載不可（PDF・private情報）のときだけignore。「gitignoreのデフォルト」は「公開予定 && 転載不可ソース → ignore+manifest、それ以外 → 追跡」の1行トリガー規則に還元できる
- このrepoのgitignoreは**grasp scaffoldからの継承**（判断プロセスの記録なし、[[リポジトリ分析 grasp]]）で、現状のソースはすべて転載可能なものばかり＝**過大適用気味**。例外構成の実証例であり、デフォルト構成の実証はfresh wikiで行うべき（バイアス顕在化の実例）

### コーパスモード（ライブ型の条件付き正当化）

nishioの `external_brain_in_markdown`（24,000ページ）はアンチパターンではなく、**「再生成可能な大規模コーパスモード」**として応用編に明示提供すべき。ただし実証は若い（n=1・約2ヶ月、コーパスドリフトによる検証可能性劣化は未実証）。

応用編に書くべき条件:
1. 再生成可能性は「**自分が管理する原典から導出可能**」が基準（publicであるだけでは不十分。repo削除・force pushで再生成不能 → [[GitHubリポジトリ分析の方法論]]）
2. 用途は発見・掘り出しに限定。結論の根拠になる引用はスナップショットpath（引用時アーカイブ）に乗せる。keyword-searchページは「全ページ→引用断片」に単位を下げた選択的スナップショットと解釈でき、作文リスクの防衛線は維持される
3. clone URL+取得日はコミットされる場所に記録（.gitignoreコメント・AGENTS.md・manifest）
4. 追従は再clone+新旧比較（`git pull`のままだと過去状態が消える）

実務は二者択一ではなく**ハイブリッドが標準**（about-nishio: bundle追跡+コーパスignore、このrepo: 発見層+引用時アーカイブ）。判断基準は「全量アーカイブのコスト vs 時点固定の検証価値」。

## claims候補（草案ver.2、subagent相談から）

**デフォルトAGENTS.md（1-2行、既存1行の延長）**:

```
raw/ — アーカイブ層。LLMができるのはアーカイブの新規追加と raw/manifest.md への追記のみ。
       書き込んだファイルはその時点の内容で凍結される（更新は新規追加で表現。既存の変更・削除は禁止）。
```

**scaffold（.gitignore）**: デフォルトに `raw/*` のignore行を**含めない**（追跡デフォルト）。例外手順は応用編: 「公開予定 && 転載不可ソース → `raw/*` ignore + `!raw/manifest.md`」。manifest.mdは両構成でコミット対象（既仮採用）

**応用編（デフォルトに書かない）**: 入場テスト1文 / 変換・整形は入場時のみ許可 / コーパスモードの条件4つ / 発見層の位置づけ（薄さ維持と整合）

## 位置付けの再評価: raw/ は補助装置（2026-09-03 補遺）

[[LLM Wikiのmain value]] の議論により、raw/ SSOT は **補助装置** に位置付けられることが明確化された。
このページの従来の議論（不変性の3機能・コーパスモード・入場時の誓約）はそのまま有効だが、
**「raw/ が wiki の main value の中心である」という暗黙の前提は撤回** する。

### 補助装置としての raw/ の 4 機能

| 機能 | 補助としての役割 |
|---|---|
| 検証可能性 | knowledge network の**信頼性を増す** |
| 作文リスク防衛 | knowledge network の**完全性を保護** |
| ライセンス・帰属台帳 | **法的・倫理的境界の管理** |
| LLM 範囲境界 | **権限マップ**（LLM書込権の境界） |

### 「再生成可能なら gitignore 可」の含意

コーパスモードの正当化原則（nishio about-nishio 由来）は、raw/ を source of truth として扱うか
単なる参照層として扱うかの**選択可能性**を含意する。これは raw/ を wiki 全体の source of truth
と扱う前提（過剰解釈）の自然な解消。

- AGENTS.md L16「LLM は読むだけで、絶対に変更しない」→「LLM は変更しない（例外: 人間依頼時の追加）」に弱める
- ingest SKILL.md にライブソース URL対応の1行追加
- 「wiki ページにも frontmatter 推奨」原則は**撤回**（知識の network 中心モデルでは過剰）
