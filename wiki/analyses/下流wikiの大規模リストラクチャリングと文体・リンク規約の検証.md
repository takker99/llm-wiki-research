# 下流wikiの大規模リストラクチャリングと文体・リンク規約の検証

下流wikiの2件目である[[txa-xray-ct-wiki]]（ガラスビーズ三軸弾性波+X線CT同時計測実験の記録wiki、コードrepo一体型、154ページ）において、ページ群・スクリプト群の大規模リストラクチャリングと文体・リンク規約の適用実験を行い、その全変更差分を5つのクラスタに分類して人間と監査した（2026-11-02〜11-03）。

本ページは、その実験と手戻りから得られた以下3つのテンプレート設計知見（`#template-design`）を記録する。

1. **`wiki/analyses/` のテーマ別フォルダコロケーションと非ドメイン運用文書の `docs/` 分離**
2. **ページ内2回目以降の `[[wikilink]]` 取り外し規則の撤回と `SAME_LINE_DUPLICATE` への転換**
3. **機械的文体リンターの過剰規制が「研究ノート構造（箇条書き・表・Callout）」を破壊するアンチパターン**

---

## 1. ディレクトリ境界とテーマ別フォルダコロケーション

### 観察された問題

[[txa-xray-ct-wiki]]では約2ヶ月の集中運用で `wiki/analyses/` 直下に135ファイルが蓄積し、以下の3種類の混在が起きていた。

- **非ドメイン運用文書の混入（62ファイル）**: ポスター発表の構成案・QA台本（16本）、ワークステーション環境移行・ジョブ実行手順・ビューアUI仕様・会議メモ・wiki自体の運用メタ文書（46本）が、実験データの分析ページと同じ `wiki/analyses/` に並んでいた。
- **基礎概念・文献サーベイの混入（10ファイル）**: 個別実験データの検証ではなく、DEMの先行研究比較やCTアーチファクト除去手法の分類など、本来 `wiki/concepts/` に置くべき一般理論ページが `analyses/` に置かれていた。
- **日付付き断片ページの乱立とルート `scripts/` の肥大化（73ファイル＋スクリプト群）**: `2026-09-14 ...`、`2026-10-13 ...` のように実験ステップごとの断片ページが増殖し、どのページが最新・正本の結論か判別しにくくなっていた。さらに特定の分析ページ1枚のためだけのプロット生成スクリプトや一時検証スクリプトがルートの `scripts/` に置かれ、汎用モジュールと混在していた。

### 採用した構造と設計原則

1. **運用文書・発表準備の `wiki/` 外への分離**:
   - ポスター関連文書を `poster/docs/`（16本）へ、解析手順書・開発規約・環境構築・会議メモを `docs/`（46本）へ移動した。
   - `wiki/` 配下は純粋なドメイン知識ネットワーク（`concepts/`・`entities/`・`sources/`・`analyses/`）に限定し、手順書等への参照は通常のMarkdown相対リンク `[手順書](../docs/...)` で接続する。
2. **一般理論・文献サーベイの `wiki/concepts/` への抽出**:
   - 実験固有の数値検証を含まない理論整理・文献サーベイ10本を `wiki/concepts/` へ移設・統合した。
3. **`wiki/analyses/<テーマ名>/` によるテーマ別フォルダコロケーション**:
   - 残る73本の実験分析ページを、日付プレフィックスを廃した12個の実験テーマフォルダ `wiki/analyses/<テーマ名>/` に統合した。
   - 各テーマフォルダ内に以下をコロケーション（同居）させる:
     - `<テーマ名>.md` — 仮説・方法・結果・考察・結論・未解決の問いを一元化したテーマ正本ページ
     - テーマ固有の解析・作図スクリプト（`*.py`）
     - 生成された図表（`*.png` / `*.svg`）および集計データ（`*.json` / `*.csv`）
   - ルートの `scripts/` には、複数テーマから `import` される共通ライブラリ・パイプライン基盤のみを残す。

### リファクタリングと日常運用におけるモデルの役割分担

当初、「日本語や構造化が不安定な軽量モデル（GLMやBeam等）でも無秩序なwikiをリファクタリングできるよう、Schemaと機械lintをガチガチに固める」方向を試みたが、これは設計上の誤りであった。

- **一度きりの大規模整理（カオス→構造化）**: フロンティアモデル（Gemini Pro / DeepSeek等）で実行すればよく、軽量モデル向けに過剰な矯正規則をSchemaに書き込む必要はない。
- **日常の継続運用（Ingest / Query / File-back）**: きれいに構造化された後のwikiでは、[[Cosense Skillとgraspに学ぶQuery近傍読解とIngest書き込み設計]]の通り「同じディレクトリの直近ページを1〜2枚読んでスタイルを合わせる」原則が効くため、Schemaを薄く保った方が軽量モデルでもコンテキスト圧迫を起こさず安定して書ける（[[Instruction Dilution]]）。

## 2. ページ内2回目以降の `[[wikilink]]` 維持と `SAME_LINE_DUPLICATE`

### 観察された問題：「初出1回のみリンク」規則の実害

[[Cosense Skillとgraspに学ぶQuery近傍読解とIngest書き込み設計]]で導入した「同一ページ内の同じページへのリンクは初出1回だけ。2回目以降は平文にする」という規則（および `lint.sh` のページ内重複リンク検出）を [[txa-xray-ct-wiki]] の105ファイルに適用し、654行の2回目以降の `[[wikilink]]` を平文化した。しかし、人間によるレビューで以下の重大な欠陥が判明した。

1. **誤字・表記ゆれの検出力喪失**: 2回目以降の言及を平文にすると、概念名やページ名を誤記しても `lint.sh` の `OPEN_LINK (1 page)` 検査に引っかからず、サイレントに表記ゆれが蓄積する。
2. **ページ統合・改名時の自動追従漏れ**: `[[ページ名]]` のままであれば、ページの統合や改名時にリンク文字列の機械的な走査・一括置換で漏れなく追従できるが、平文化されていると本文中の言及箇所が旧称のまま取り残される。
3. **長大ページでのナビゲーション劣化**: `analyses/` のような長大な統合ページでは、冒頭で1回リンクされただけの概念が数百行下の考察節や比較表で再登場した際、平文になっているとそこから参照先ページへ辿れない。

### 転換後の規則

⚠ Contradiction: [[Cosense Skillとgraspに学ぶQuery近傍読解とIngest書き込み設計]]の「同一ページ内の重複リンク却下（初出1回のみリンク、2回目以降は平文）」 vs [[txa-xray-ct-wiki]]での実運用検証（2回目以降の `[[ ]]` を外すと誤字検出と改名追従が壊れるため、ページ内の複数回 `[[wikilink]]` は維持すべき）

- **ページ内2回目以降の言及も `[[wikilink]]` を維持する**: 異なる段落・節・表セルで同じ概念やソースに言及する場合、`[[...]]` を外さずリンクのまま残す（[[txa-xray-ct-wiki]]では平文化していた約500箇所の `[[wikilink]]` をすべて復元した）。
- **禁止するのは「見出し内のリンク」と「同一行内の重複リンク（`SAME_LINE_DUPLICATE`）」のみ**:
  - 見出し行（`# ...`）にはリンクを置かず、直後の本文でリンクする。
  - 複数の旧ページを1つの新テーマページへ一括置換した際などに、1行（1文や関連ページの1箇条書き行）の中に `[[同じページ]]...[[同じページ]]` が重複して並ぶ事故だけを `lint.sh` の `SAME_LINE_DUPLICATE` で機械検出する。

## 3. 機械的文体リンターの過剰規制による「研究ノート構造の散文化」

### 実験内容：6つの機械的スタイル検査の導入

[[日本語矯正Agent Skill群の設計空間]]で議論された「低コストLLMの日本語劣化・圧縮構文の抑制」を意図し、`txa-xray-ct-wiki` の統合フェーズで `lint.sh` に以下の8項目の機械検査を導入して違反0件を強制した。

- `CHAR_DRIFT`: 簡体字・繁体字の混入（例: `径`→`徑`、`変`→`變`）
- `STYLE_SPACE`: 和欧間の不要な半角スペース（例: `CT 画像`）
- `STYLE_NOMINAL`: 体言止め（文末が漢字・カタカナ・閉じ括弧等で終わる行）の禁止
- `STYLE_PAREN`: 本文中の丸括弧 `（...）` / `(...)` による補足の禁止
- `STYLE_BOLD`: 本文中の太字 `**...**` の禁止
- `STYLE_SLASH`: スラッシュ `/` による並記（`load/relax` 等）の禁止
- `STYLE_ARROW`: 矢印記号 `→` の禁止
- `STYLE_EMDASH`: ダッシュ `—` / `―` の禁止

### 観察された副作用（5クラスタ監査の結果）

統合後の全ページを人間と監査した結果、後半の6検査（`STYLE_NOMINAL`〜`STYLE_EMDASH`）をパスさせるために、LLMが**研究ノートとして最も重要な視覚的構造と技術的ディテールを破壊していた**ことが判明した。全変更をクラスタリングした5類型のうち、問題となった代表例は以下の通りである。

| クラスタ | 発生した現象 | 具体例（Before → Bad Rewrite） | 評価 |
|---|---|---|---|
| **Cluster 1: 散文の明晰化・主述接合** | 和欧間スペース除去、簡体字除去、主語と述語がねじれた悪文の修正 | `CT 画像` → `CT画像`、破綻した長文の分割 | **良（維持）** |
| **Cluster 2: 箇条書き・順序要素の1段落散文化** | 体言止め・太字・括弧・矢印の禁止を回避するため、LLMが箇条書きや番号付きリストを「第1に…である。第2に…である。」という1段落の論文調散文へ平坦化 | `- **P1（システム遅延）**: ...` / `- **P2（減衰）**: ...` の優先度付きリスト → `第1の要因はシステム遅延のドリフトである。…第2の要因は…` のベタ書き1段落 | **悪（可読性悪化・全面復元）** |
| **Cluster 3: 比較表・Callout・図解の散文化** | 表記制約や統合時の要約圧力により、`> [!WARNING]` CalloutやMarkdown比較表、ASCII概念図を通常の地の文に埋め込み | `> [!WARNING] 敵対的レビューで判明した3つの限界` Callout → 通常の段落文へ吸収され警告性が消失 | **悪（視認性喪失・全面復元）** |
| **Cluster 4: 検証プロセス・検死記録・文献表の脱落** | 「結論を簡潔な散文で書く」圧力により、バグの検死プロセス（符号ミス、ラジアン/度取り違え）、棄却仮説の検証数値、60本超の先行研究表（DOI付き）が省略 | ラジアンと度の取り違えで $95.6\% \to 82\%$ の誤結論に至った検死記録、1Dスカラー減算から3D運動学への移行経緯が数行の一般論に短縮 | **悪（情報欠損・全面復元）** |
| **Cluster 5: メタデータ・リンク正規化** | 旧ページリンクの新テーマ名への更新、一方で2回目以降の `[[wikilink]]` 剥離 | `[[旧ページ]]` → `[[新テーマ名]]`（良）、2回目以降の `[[...]]` 平文化（悪） | **リンク更新は維持、剥離は復元** |

### 導かれた設計原則：「論文調の散文」ではなく「構造化された研究ノート」

1. **機械的文体検査は「構造を壊さない表層バグ」のみに限定する**:
   - `lint.sh` で機械検査してよいのは **`CHAR_DRIFT`（簡体字・繁体字混入）** と **`STYLE_SPACE`（和欧間の不要な半角空白）**（およびリンクの **`SAME_LINE_DUPLICATE`**）のみ。
   - 体言止め・丸括弧・太字・スラッシュ・矢印・ダッシュを機械的に禁止すると、LLMはリストやラベル付き箇条書き（`- **項目名（条件）**: A → B の変化`）を使えなくなり、すべてを冗長な散文段落へ書き換えてしまう（[[日本語矯正Agent Skill群の設計空間]]の「モグラ叩き」が構造破壊の形で発現した実例）。
2. **`AGENTS.md` で求める文体は「視覚的に構造化された研究ノート」とする**:
   - 並列要素（要因の列挙、メリット・デメリット、領域別の特徴）は**箇条書き（`-`）**で書く。
   - 順序要素（実験手順、アルゴリズムのステップ、優先順位 P1→P2→P3）は**番号付きリスト（`1. 2. 3.`）**で書く。「第1に…第2に…第3に…」と1段落の文章に繋げてはならない。
   - 複数条件×複数指標の対比は**Markdown表**で整理し、重要な前提条件（正本データ系列の切替、測定限界、バグ検死の教訓）は **GitHub Alert（`> [!WARNING]` / `> [!IMPORTANT]` / `> [!NOTE]`）** で視覚的に際立たせる。
3. **科学的な試行錯誤の系譜（バグ検死・棄却仮説）を要約で消さない**:
   - 統合ページであっても、「どの仮説がどの数値で棄却されたか」「どのコードバグ（符号・単位・軸定義）がどう発見・修正されたか」という実証の経緯は、結論の信頼性を支える中核情報であり、散文要約で削ぎ落としてはならない。

## テンプレート（`template/`）への反映事項

本検証に基づき、当リポジトリの `.agents/` および配布用 `template/` に以下を反映した。

1. **`llm-wiki-write/SKILL.md` / `llm-wiki-lint/SKILL.md`**:
   - 「同一ページ内の同じページへのリンクは初出1回だけ。2回目以降は平文にする」を削除し、ページ内2回目以降の言及も `[[wikilink]]` を維持する規則（見出し内リンクと同一行内の重複リンク `SAME_LINE_DUPLICATE` のみ回避）に改訂。
2. **`lint.sh`（研究wiki本体および `template/`）**:
   - ページ全体の重複リンク検査（`DUPLICATE`）を廃止し、同一行内の重複リンク検査（`SAME_LINE_DUPLICATE`）に置換。
   - `analyses/<テーマ名>/<テーマ名>.md` のようなサブディレクトリ構成でもOrphan検査・frontmatter検査・相対画像リンク検査が機能するよう拡張。
   - Markdown表内のエスケープパイプ付きリンク `[[Page\|Alias]]` で末尾の `\` が残るパース不具合を修正。
3. **`template/.agents/scripts/search-pages.sh`**:
   - `--catalog` 出力時のディレクトリ見出しを最上位ディレクトリ（`analyses` 等）単位でグルーピングするよう修正し、テーマ別サブディレクトリ使用時に見出しが細分化されないようにした。
