## 横断的発見

### 1. AGENTS.mdサイズを決める要因（5件に拡張）

```
AGENTS.mdサイズ = f(skillの有無, プロジェクト複雑性, ツール依存度, ドメイン特化度)
```

| 条件 | 例 | サイズ |
|---|---|---|
| skillあり + 低複雑性 | AMME | 1.9KB |
| skillなし + 中複雑性 | about-nishio | 6.4KB |
| CLAUDE.mdのみ + 中複雑性 | delite | 7.5KB |
| skillなし + 高複雑性（ツール開発込み） | grasp | 12.5KB |
| skillあり + 高複雑性（SSOT分配） | BDL-2026S | 15.8KB |

**新発見**: BDL-2026Sはskillあり（.agents/ 4件）だが15.8KB。SSOT分配設計（50行）と講義特化ルール（42行）がskillでは吸収しきれないドメイン複雑性を持つ。**skillは「操作手順」の外部化には有効だが、「ドメイン知識の構造化」の外部化には限界がある。**

### 2. index.md/log.md 配置の2派

| 派 | 代表 | 特徴 |
|---|---|---|
| ルート直下派 | about-nishio (1/5) | AGENTS.mdからの即時参照。少数派 |
| wiki/配下派 | grasp, AMME, BDL, delite (4/5) | wiki/が自己完結。多数派 |

テンプレートのデフォルトはwiki/配下が自然。ルート直下はコードやツール設定と混在するリスクがある。

### 3. AGENTS.md=CLAUDE.md 管理の4パターン（拡張）

| パターン | 例 | リスク |
|---|---|---|
| 完全コピー | about-nishio | 同期漏れ |
| 共通部分コピー+差分分離 | grasp | 二重メンテナンス |
| CLAUDE.mdのみ（AGENTS.mdなし）| **delite** | ツール依存。他LLMツールからアクセス不可 |
| CLAUDE.mdなし | AMME, BDL | opencodeのみ。ただし移植性が低い |

deliteのCLAUDE.md-onlyパターンは、ツールに最適化しすぎると移植性を失うことの教訓。

### 4. メタデータ戦略のスペクトラム（拡張）

| 戦略 | 例 |
|---|---|
| frontmatterフル（type+summary+sources+tags+dates+status） | about-nishio, grasp, BDL |
| frontmatter詳細（読み・種類・一言要約・詳細・関連用語・ソース） | delite（CLAUDE.mdで規定） |
| frontmatter最小（source: 行のみ） | AMME |
| frontmatterなし | AMMEのconcept/entityページ |

### 8. 停止パターンの2類型（新規）

| 型 | 例 | 特徴 |
|---|---|---|
| **完了型停止** | delite | 目的達成後に自然停止。未着手は多いが「complete」で満足 |
| **進行中型** | 他4件 | 更新継続中または緩やかな停止 |

deliteは「失敗」ではなく「成功裏の完了」と解釈すべき。43時間で目的達成している。

### 9. init.txtパターン（新規）

deliteの `init.txt`（427 bytes）と grasp/BDLの初期setup:
- 極小の初期指示でWikiを立ち上げるパターン
- deliteでは誤記（宇多川→宇田川）をCLAUDE.mdで訂正する二重管理が発生
- **教訓**: 初期指示の誤りは元ファイルで訂正すべき。テンプレートにはinit指示と運用ルールの分離が必要

### 10. 命名規則の2派（新規）

| 派 | 例 | 特徴 |
|---|---|---|
| 自然言語（日本語） | about-nishio, delite | 検索性高、移植性低 |
| kebab-case英語 | AMME, BDL | 移植性高、日本語話者に不親切 |
| 移行計画中 | BDL（concept-rename-mapping.md） | kebab-case→自然言語へ128件マッピング |

BDLの `concept-rename-mapping.md` は命名方針の明文化としてテンプレート設計に資する。

### 11. graspの名目利用と実利用の乖離（新規）

BDL-2026SはAGENTS.mdでgrasp運用を定義しているが、wiki.grasp/ のeventsは7件のみ。
実運用はLLMがファイルシステムを直接操作。graspは「設計上の意図」に留まり、
**ツールの導入が運用の実態に追いついていない**パターン。

### 12. パイロットの分類ラベルは目的ラベルでありrepo型ラベルではない（新規・2026-08-14）

比較表の「型」列（個人成熟 / Code+Wiki / 研究レポート / 講義 / 逸脱・停止）はすべて**目的**による分類であり、repo型（同一repo vs 別repo参照）を表していない。**目的とrepo型は直交する軸**（[[Wikiとコードリポジトリの関係]]）。実際、同一repo型のgrasp・BDL-2026Sは知識の蓄積が主目的、別repo参照型のdd2030-wiki・kouchou-ai-developer-wikiはプロジェクトの記憶・成果物管理が主目的で、単純な対応は成り立たない（BDL-2026SのREADMEでは主目的をcompounding knowledge baseと明記）。repo型の選択基準（コードの有無→生まれ方→知識の向き→公開性）は目的分類とは独立に扱う。

### 13. 第6のデータ点: 実装repo（ツール）型（新規・2026-08-14）

[[リポジトリ分析 microsoft-llmwiki]] は運用repo（wikiがコンテンツ）ではなく**実装repo**（wiki運用をソフトウェア化する製品）。比較表の枠組み（AGENTS.mdサイズ・ページ数・運用期間）は適用不能で、別レンズ（設計判断・操作層の実現手段）で分析する。
- 3層構造・index/log形式が当wikiとほぼ同一 → 構造の普遍性の独立確認（横断所見#1, #2の補強）
- 操作層をツール型（MCP/拡張）で実装 → [[操作層]]の概念を新設
- broken-links=error のハードライン（[[Lint]]赤リンク論争のデータ点）
- 差別化の軸は「操作層を文書で提供するかツールで提供するか」
