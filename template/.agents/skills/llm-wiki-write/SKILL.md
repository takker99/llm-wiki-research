# Wiki Write (Ingest / File-back)

外部ソースのingest、またはQuery回答・対話で生まれた知見のfile-backによって、`wiki/`のページを作成・更新し知識ネットワークに編み込む操作。
ディレクトリ構成・命名・機械要件は`AGENTS.md`に従う。

## 手順

1. 入力を用意する
   - Ingest時: 対象ソースを読む。PDF等の非テキストソースは、まずテキスト抽出して読む。図表が重要と判断したページのみ、当該ページと前後数ページを画像化して読む
   - 外部URLソースは、人間からアーカイブの指示があれば `raw/` に保存し、なければ `source_url:` で参照する
   - File-back時: 人間が承諾したQuery回答や対話の知見を入力として手順2へ進む
2. 既存ページとの接続点・文脈・スタイルを把握する
   - `bash .agents/scripts/search-pages.sh "<検索語>"`で既存ページとの接続点と未カバー領域を特定する。全体像が必要な時は`bash .agents/scripts/search-pages.sh --catalog`で全ページの要約付きカタログを出力する
   - 更新候補の既存ページと、新規作成予定の概念名に言及している既存ページを`bash .agents/scripts/read-page.sh "<タイトル>"`で読む。新規作成のつもりでも、すでに複数ページから未作成リンクとして言及されている文脈がないか確かめる
   - 新しくページを作るディレクトリの直近のページや近いテーマの既存ページを1〜2枚読み、見出しの立て方、frontmatterの項目、記述の粒度を観察して合わせる
3. 要点と編み込み計画を人間と議論する
   - Ingest時: ソースの要点3〜5個と、どの既存ページを更新し何を新規ページとして切り出すかの編み込み計画を提示し、何を重視するか聞く
   - File-back時: 提案時に作成・更新対象が合意済みであればそのまま手順4へ進む
4. ページを作成・更新する
   - Ingest時は`wiki/sources/YYYY-MM-DD タイトル.md`を作成する。要約、関連する`concepts/`・`entities/`へのリンク、情報源へのポインタを含める。既存の`sources/`ページの本文を書き換えた時も手順5に従い、同じ編集で`summary:`を見直す（要約の過去の状態はgit履歴で参照できる）
   - 新規の`concepts/`・`entities/`・`analyses/`ページを作成し、関連する既存ページと相互に`[[wikilink]]`を張る
   - 影響を受ける既存の`concepts/`・`entities/`・`analyses/`ページを更新する。既存の主張と矛盾する場合は「⚠ Contradiction: [旧主張] vs [新ソース]」の形式で明示する。複数ソース間の比較や矛盾の分析が長くなる場合は`analyses/`にページを切り出してよい
   - 書き換え時は単なる上書きで過去の経緯を消さず、主張の訂正・仮説の棄却・数値の改定があれば「旧→新」の系譜と理由をページ内に残す
5. リンク接続を確認し、要約を同期する
   - 追加・変更したリンク表記が接続先の既存ページタイトルと一致しているか確かめる。表記ゆれで繋がっていない箇所があれば修正する
   - 新規ページは作成時にfrontmatter `summary:`（1行・1〜2文）を必ず付ける。既存ページの本文を書き換えた時は、同じ編集でそのページの`summary:`も見直す（要約は検索と`--catalog`カタログの正本）
   - `wiki/log.md`に`ingest`または`file-back`のエントリを追記し、本文に触れたページ数の内訳を記録する
   - logは追記専用。既存エントリは変更・削除しない（追記前に `git diff wiki/log.md` で確認してよい）
   - `bash .agents/skills/llm-wiki-lint/scripts/lint.sh`を実行し、孤立ページ、オープンリンク（未作成ページへのリンク）、frontmatterの欠落、画像リンクの解決がないか機械検証する。オープンリンクは欠陥ではないので、表記・パス形式の確認だけ行い、意図的なものは残す

## 内部リンクの選定基準

リンク記法`[[タイトル]]`はナレッジグラフへの接続として選ぶ。
主張単位の出典引用は`[[ソースページ]]`（claim粒度引用。ページ番号がある場合は`p.XX`を添える）の形を基本にする。

- 採用するリンク
  - ページの主題を構成する中心概念であり、既存ページまたは複数ページが共有する未作成概念に繋がる語。ソース内の同義語や表記ゆれが既存ページを指す場合は、既存ページタイトルに表記を揃えてリンクする
  - 将来複数のソースや議論が接続する明確な未解決概念
- 却下するリンク
  - ページの主題を構成しない周辺的な固有名詞や一般語
  - 主題と直接関係のない、被リンク数が突出したハブページへのリンク
  - 文字列は一致するが文脈が異なるページへのリンク
  - 一覧・点呼内に列挙される他項目名（主題を構成しない点呼）。substantiveな記述が付く場合は、その主張の箇所で接続する
  - 同一行内の重複リンク（`SAME_LINE_DUPLICATE` — 1つの行・文の中に同じページへの`[[リンク]]`が複数回出現するもの）

ページ内の異なる段落・節・表セルで同じページに2回目以降言及する場合も、`[[リンク]]`を外さず維持する（リンク走査による誤字検出とページ改名時の追従を保つため）。見出し内にはリンクを置かず、見出しの主題は直後の本文でリンクする。

## 新規ページの作成

新規ページは、2ページ以上から参照される未作成リンクの昇格、または複数ページが共有する未作成概念の集約として作る。ingest対象ソースの中心概念はこの限りではなく、手順4でsourcesページからリンクして切り出す。entityを散在する言及から新規作成する時は、点呼的な言及ではなくsubstantiveな記述（仕様・数値・手順等の内容が付くもの）だけを集約する。

## sourcesページのfrontmatter形式

```yaml
---
summary: "1行・1〜2文の要約"
raw: "raw/ファイル名.md"
source_url: "https://..."
accessed: YYYY-MM-DD
---
```

情報源へのポインタとして`raw:`または`source_url:`を1つ以上含める。両方ある場合は両方書く。どちらも書けないソースはingestしない。

- `raw:` — `raw/`からのファイルパスを書く
- `source_url:` — URL参照ソースのURLを書く。リポジトリの場合は検証できるよう`commit:`に参照時のcommit hashを固定して併記する
- `accessed:` — 外部URL等を参照・取得した日を書く任意項目
